## Section 5b: Gap-hunt probes (beyond the checklist — tester-added)

Per dispatch brief step 3 ("probe for gaps the matrix might mask"). Five probes written to `tests/one-offs/thinking/probe_53_gap_hunt.py` (throwaway/exploratory tier — not promoted into the shipped suite, since two reveal CODE gaps that need a maintainer decision, not a tester-authored "expected" assertion). All 5 probes ran clean (5 passed); findings below are about the PRODUCTION BEHAVIOR they observed, not about probe pass/fail.

- [x] **P1 — `agent_context` that normalizes to empty** (e.g. `agent_type="___"`): `normalize_subtype("___")` → `None` (three non-alnum chars collapse to one `-`, `rstrip("-.")` empties it). Traced through `_collect_channels_for_entry` (`logger.py` line ~382-387): `raw="___"` passes the `if not raw` guard (truthy), but `if not normalized: continue` then silently skips the channel. **Observed: the agent's internal tool calls vanish from the agents channel ENTIRELY — not just from subtype splitting, from the base `.agents_` file too** — while the same calls appear normally in `.shell_`. Only the dispatch entry (routed via the `meta` category, independent of `collect`) still lands in base `.agents_`. **CODE GAP, reported not fixed. Severity: LOW** — agent type names come from a controlled registry (Explore, oracle, senior-engineer, ...), so an all-illegal-char type name is not a realistic near-term scenario, but the failure mode is a *silent, total* drop rather than a graceful fallback (e.g., an `unknown`/raw-value bucket), which could hide real agent traffic during future debugging if a future agent-naming scheme ever produces such values. **Disposition: carried as a Decision Ledger deferral in the #53 design doc** (graceful-fallback bucket design when reopened; not fixed in the shipping commit).
- [x] **P2 — collect list-form with an empty list** (`{"agent_context": []}`): `_collect_channels_for_entry` returns `{}` for any entry — vacuous-safe, matches "collect only these listed values, and there are none" semantics. **No gap; confirmed-safe.**
- [x] **P3 — channel with `collect` declared but `enabled: false`**: set `agents.enabled = False`, left `collect={"agent_context": True}` and `subtype_split=True` (a fully plausible real config — user disables the channel without also clearing its options). **Observed: the base `.agents_` file correctly does not get created (the write-loop's enabled check catches the literal `"agents"` channel name) — but the derived `.agents-explore_*` subtype file IS still created and written with full content.** Root cause: `log_entry`'s enabled check (`logger.py` line ~445-447) does `self.config.routing.channels.get(channel_name)` keyed by exact name; derived names like `"agents-explore"` are never a literal key in `routing.channels` (only `"agents"` is), so `channel` resolves to `None` there and the `if channel and not channel.enabled` guard never fires for the derived channel. **CODE GAP, reported not fixed. Severity: MEDIUM** — this is not #53-specific (the same code path existed for pre-#53 category-driven subtype_split), but #53 makes it far more reachable in practice: `agents` is the one channel that ships `collect` + `subtype_split` both on by default, so "disable the agents channel" is a realistic user action that silently fails to suppress `.agents-<type>_*` output. A user disabling the channel for output-volume or privacy reasons would reasonably expect zero `.agents*` files, not a partial leak. **RESOLVED same-day: fixed in the shipping commit** -- the enabled check now inherits the base channel's flag for derived names (same literal-first-then-base idiom as `_get_channel_path`/`_resolve_channel_options`); sanctioned regression test `TestDisabledChannelSuppression`; mutation M11 KILLED; suite 449; snapshot still byte-identical.
- [x] **P4 — Agent dispatch payload with `subagent_type` key entirely absent** (not empty string — missing key): dispatch entry lands cleanly in base `.agents_` only, no subtype file, no crash. **No gap; graceful degradation confirmed as designed.**
- [x] **P5 — duplicate `SubagentStop` events** (identical payload fired twice): report marker (`REPORT-P5-MARKER`) appears **twice** in both `.agents-explore_*` and `.convo_*`. `conversation.py`'s Stop/SubagentStop handler has no dedup/sentinel — every call unconditionally appends. **Not a gap — by-design consequence of the append-only logging philosophy** (any duplicated hook event duplicates its log line, consistently across the whole pipeline, not just the #53 report leg). Documented here since nothing in the shipped suite exercised it.
