# Human Test Checklist: Entry frame integrity ("the braces always match")

**Target version:** v0.3.18
**Ships with commit:** TBD (pre-commit) -- "v0.3.18: entry frames always match; the body stays verbatim"
**Companion automated tests:** 81 tests in `tests/one-offs/test_render_frame.py` (23 proven as anchors by reverting the dispatch call); mutation sweep `tests/mutation/v0.3.18__sweep__u4-frame-padding.md` (12 of 12 killed); snapshot suite `tests/snapshots/diff_check.py` byte-identical; full suite 610.

## What this is

Every log entry is framed as `{LABEL: body }` on one line, or `{LABEL:` / body / `}` in the multi-line `convo` channel. The way to walk a log is the editor's brace jump (vim `%`, VS Code "Go to Bracket") from an entry's first `{` to its last `}`. Editors count every brace in a plain-text file, so a body containing an unmatched brace -- a prompt that quotes a log entry, a shell command like `echo "{"`, a truncated preview -- used to leave the frame unmatched. From v0.3.18 the body is still recorded verbatim, and the balance is restored **outside** the frame: one extra `}` after the closing brace per unmatched `{` in the body, one extra `{` after the opening brace per unmatched `}`. Balanced bodies get no extra braces at all.

This checklist is for a person with an editor and a terminal. The automated tests prove the string transformation; only a person can prove the jump lands, the flat body reads well under `tail`, and a real quoted prompt survives the round trip.

## Prerequisites

1. Claude Code with the session-logger plugin at v0.3.18 or later (`python -c "import version; print(version.__version__)"` from the plugin root, or check the plugin list).
2. A throwaway project directory to start test sessions in, so the log files you inspect are clearly yours. Session logs land under `~/.claude/sesslogs/<session-name>__<session-id>_<user>/`; nothing in this checklist writes anywhere else.
3. vim (or any editor with `%`) and VS Code, for the navigation checks.
4. For Section 3 only: the plugin's config file. Back it up before editing and restore it in Cleanup.

**Reset between sections:** start a fresh Claude Code session in the throwaway directory; each session gets its own log directory. Nothing else needs resetting.

**Finding the session's log directory** (pick your shell):

**cmd.exe**:
```cmd
dir /b /o-d "%USERPROFILE%\.claude\sesslogs"
```

**PowerShell**:
```powershell
Get-ChildItem "$env:USERPROFILE\.claude\sesslogs" | Sort-Object LastWriteTime -Descending | Select-Object -First 3 Name
```

**POSIX**:
```bash
ls -t ~/.claude/sesslogs | head -3
```

The newest directory is your session. Inside it the channel files are hidden dot-files: `.convo_*`, `.sesslog_*`, `.shell_*`, `.tools_*`.

## High-Value Verification (~5 minutes)

**If you only have 5 minutes**, run these five. They are the reason the change exists.

### HV.1 -- A quoted log entry in a prompt does not break the frame

Validates: the multi-line `convo` channel pads an unmatched `{` after the closing brace, and the body is byte-verbatim.

- [ ] **Steps:**
  1. In a fresh session, send this prompt exactly (it contains one unmatched `{`):
     ```
     Please echo back this line verbatim: things to do:{
     ```
  2. Open the session's `.convo_*` file in vim, put the cursor on the `{` of the `{USER:` line for that prompt, press `%`.
- [ ] **Expected:** the cursor lands on the `}` at the end of that entry, which now reads `}}` (the frame's `}` plus one extra). The body line `things to do:{` appears exactly as typed, with nothing inserted into it.
- [ ] **Why this matters:** this is the failure that triggered the fix -- a body brace stealing the frame's partner so a logical row could not be bounded.

### HV.2 -- A shell command with a stray brace pads the single-line channels

Validates: the same rule in `.shell_*`, `.sesslog_*` and `.tools_*`.

- [ ] **Steps:**
  1. Ask Claude to run: `echo "frame demo: one stray open brace {"` and then `echo "frame demo: one stray close brace }"`.
  2. View the two lines (pick your shell):

     **cmd.exe**: `findstr /C:"frame demo" "%USERPROFILE%\.claude\sesslogs\<your-session-dir>\.shell_*"`
     **PowerShell**: `Select-String -Path "$env:USERPROFILE\.claude\sesslogs\<your-session-dir>\.shell_*" -Pattern "frame demo"`
     **POSIX**: `grep "frame demo" ~/.claude/sesslogs/<your-session-dir>/.shell_*`
- [ ] **Expected:**
  ```
  [[...]] {Bash: echo "frame demo: one stray open brace {" }}
  [[...]] {{Bash: echo "frame demo: one stray close brace }" }
  ```
  The first line ends with two `}`; the second starts with two `{`. The commands themselves are untouched.
- [ ] **Why this matters:** the rule must hold in every channel, not only the conversation file.

### HV.3 -- Balanced bodies are byte-identical to before

Validates: no padding is added when nothing is unmatched.

- [ ] **Steps:**
  1. Send a prompt containing a balanced block, for example: `re:{ this is balanced }` followed by a second line `and {nested {a} b} too`.
  2. Find the entry in `.convo_*`.
- [ ] **Expected:** the entry opens `{USER:` and closes with a single `}` on its own line; the body is exactly what you typed.
- [ ] **Why this matters:** every existing log on disk contains balanced entries; they must not change shape.

### HV.4 -- VS Code bracket jump

Validates: the second editor the maintainer uses agrees with vim.

- [ ] **Steps:**
  1. Open the same `.convo_*` file in VS Code, place the cursor just after the `{` of the `{USER:` line from HV.1, run "Go to Bracket" (Ctrl+Shift+\ by default).
- [ ] **Expected:** the cursor moves to the last `}` of that entry (the second brace of `}}`).
- [ ] **Why this matters:** the fix is defined by editor behaviour, and editors pair brackets slightly differently.

### HV.5 -- The body is flat under `tail`

Validates: nothing was indented or reflowed (an indentation approach was considered and rejected).

- [ ] **Steps:**
  1. In a terminal 80 columns wide, tail the file (pick your shell):

     **cmd.exe**: `powershell -Command "Get-Content '%USERPROFILE%\.claude\sesslogs\<your-session-dir>\.convo_*' -Tail 20"`
     **PowerShell**: `Get-Content "$env:USERPROFILE\.claude\sesslogs\<your-session-dir>\.convo_*" -Tail 20`
     **POSIX**: `tail -20 ~/.claude/sesslogs/<your-session-dir>/.convo_*`
- [ ] **Expected:** body lines start at column 0 exactly as typed; the only additions anywhere are extra braces on the frame's own lines.
- [ ] **Why this matters:** the terminal is the primary reading surface; padding must not cost width.

## Section 1: The multi-line channel (`convo`)

### 1.1 Two unmatched opens

- [ ] **Steps:** send a prompt whose body is `a { b { c`.
- [ ] **Expected:** the entry's closing line reads `}}}` (three braces: the frame's plus two).
- [ ] **Check:** vim `%` from the entry's opening `{` lands on the third `}`.

### 1.2 One unmatched close

- [ ] **Steps:** send a prompt whose body is `oops }`.
- [ ] **Expected:** the entry's opening line reads `{{USER:`; the closing line is a single `}`.
- [ ] **Check:** vim `%` from the FIRST `{` of `{{USER:` lands on the closing `}`; from the second `{` it lands on the `}` inside the body (that is the padding doing its job).

### 1.3 Both kinds at once

- [ ] **Steps:** send a prompt whose body is `} and then {`.
- [ ] **Expected:** `{{USER:` on the opening line and `}}` on the closing line.

### 1.4 A pasted log entry

- [ ] **Steps:** copy any complete entry out of a `.convo_*` file (from `[[` through its closing `}`) and paste it into a prompt with one sentence before and after.
- [ ] **Expected:** the pasted lines appear verbatim inside the new entry, including their own `[[...]] {USER:` line and `}` line; the new entry's own frame still pairs under `%` because the pasted entry is balanced.
- [ ] **Why:** a quoted entry is the case no delimiter choice could have survived; balance is the only thing that works.

### 1.5 Claude's own replies

- [ ] **Steps:** ask Claude to reply with a message that ends in a single `{` on its own line.
- [ ] **Expected:** the `{AI:` entry for that reply closes with `}}`.

## Section 2: The single-line channels (`shell`, `sesslog`, `tools`)

### 2.1 Balanced command untouched

- [ ] **Steps:** have Claude run `awk '{print $1}' /dev/null` (POSIX) or `echo {balanced}` (any shell).
- [ ] **Expected:** the entry ends with a single ` }`; grep for the exact command text finds it.

### 2.2 Truncated preview

- [ ] **Steps:** have Claude write a file whose content starts with `re:{` followed by a very long balanced line (more than 200 characters before the closing `}`).
- [ ] **Expected:** in `.tools_*` (100-character preview) the Write entry shows the truncated snippet ending in `...` and the line ends with `}}`: the cut left an unmatched `{`, and the frame was balanced after the cut.

## Section 3: The pwd part (requires a config edit)

**Skip this section if** you would rather not edit the plugin config. Back it up first (Cleanup restores it).

### 3.1 Padding stays before the pwd part

- [ ] **Steps:**
  1. Back up the config, then set `"pwd_enabled": true` at the top level of `~/.claude/plugins/settings/session-logger.json` (create the file with just that key if it does not exist).
  2. Start a fresh session; have Claude run `echo "pwd demo {"`.
- [ ] **Expected:** the `.shell_*` line reads `{Bash: echo "pwd demo {" }} ["<cwd>"]` -- the extra `}` sits before the ` ["..."]` part, and the pwd part is unchanged.

## Section 4: Entries that are not the frame shape

### 4.1 Session markers

- [ ] **Steps:** in any session log, find the `SESSION START` (or `COMPACT`) marker lines.
- [ ] **Expected:** they are exactly as in earlier versions; no braces were added to them.

## What the automated tests DON'T cover

- The editor jump itself (vim `%`, VS Code "Go to Bracket") on a real file
- How the flat body reads in a narrow terminal under `tail`
- A real prompt that pastes a log entry verbatim, through the real hook
- The live hook path end to end (the tests call the formatter directly; the snapshot suite runs the hook against synthetic events, not a live session)
- `pwd_enabled` in a real config (the tests construct the pwd part directly)
- Windows console rendering of the `←` arrow in Write entries (unchanged by this fix, but visible in HV.2's neighbours)

## Reporting issues found

1. Note the section and step number.
2. Capture the exact prompt or command and the log line(s), including the `[[timestamp]]`.
3. Save the whole channel file if the entry boundary is wrong (the bug is about boundaries, so context matters).
4. File an issue referencing this checklist and the v0.3.18 commit.
